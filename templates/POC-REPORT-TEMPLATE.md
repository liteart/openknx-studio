# PoC Report: Experiment name

## Question and minimum scope

State the single technical risk, exact success criteria, exclusions, and relevant task IDs. Do not substitute an easier observation for the requested proof.

## Inputs and provenance

Record editor/fork/host commits, dependency/toolchain versions and features, original artifact filenames/hashes/sizes, selected product/application/mask/firmware, and permitted source documentation. Mark every missing input.

## Environment and authorization

Record OS/architecture/runtime, interactive-session status, ETS absence checks, bench/gateway/device identity, network isolation, approved operation and human authorization. Keep secrets and identifying household content out of public evidence.

## Reproduction

Give exact commands that were actually executed, setup state, expected observable output, result locations and cleanup/recovery procedure. Separate simulator and hardware runs.

## Observations

Record raw outcomes, errors, relevant traces, state hashes, screenshots where useful, and before/after verification. State what the evidence does and does not prove.

## Result

Technical outcome: PASS / FAIL / INCONCLUSIVE. Required tests not executed: list as NOT RUN. Acceptance criteria: satisfied/unsatisfied individually. Residual physical state: known/unknown with evidence. Independence and repository-boundary checks: explicit result.

## Blockers and next decision

Identify exact missing services/rights/inputs or failed behaviors. Recommend the smallest follow-up experiment, not a speculative replacement architecture. A FAIL/INCONCLUSIVE report is not GO for product implementation.

## Review

Human reviewer, date, reviewed source/artifact hashes, agreed limitations, and gate impact.
